# 03 · Naming & business vocabulary

> **Applies to:** every file, identifier and UI string in `frontend/`.
> **Why it matters:** names are how people and AI agents find code. One convention per kind of thing,
> and business words taken from the glossary exactly, so the code, the SRS, Figma and Jira all say the same thing.

## 1. Files and folders

| Kind | Convention | Example |
|---|---|---|
| Folder | `kebab-case` (except kit folders, below) | `features/ticket-import/`, `shared/routing/` |
| File exporting **one React component** | `PascalCase.tsx`, same name as the component | `ReviewQueuePage.tsx`, `RejectTicketModal.tsx` |
| File exporting **one hook** | `camelCase.ts`, same name as the hook | `useReviewQueue.ts` |
| Any other file | `kebab-case.ts` | `feature-routes.ts`, `query-client.ts`, `date.ts`, `handlers.ts` |
| Kit component folder in `shared/ui/` | `PascalCase/`, same name as the component | `shared/ui/StatusTag/StatusTag.tsx` + `index.ts` |
| Test | same name as the file under test + `.test` | `ReviewQueuePage.test.tsx`, `date.test.ts` |
| CSS Module | same name as its component + `.module.css` | `ReviewQueueTable.module.css` |

`shared/ui/` is the one place where folders are PascalCase, because each folder *is* one component
(component file, its CSS Module and its test together). Everywhere else folders are kebab-case.

*Why:* the file name tells you what it exports, so search ("go to file") finds it instantly. Lower-case
folders avoid trouble on Windows and macOS, whose file systems ignore case while git does not — to
change only the case of a file name, use `git mv OldName.tsx NewName.tsx`, never a plain rename.

## 2. Screens, popups and parts

| Thing | Suffix | Example | Rule |
|---|---|---|---|
| Screen (Figma frame) | `Page` | `ImportPreviewPage` | Name = SRS screen name in PascalCase. |
| Popup (Figma "(popup)" frame) | `Modal` | `RejectTicketModal`, `GiveFeedbackModal` | Name = SRS popup name + `Modal`. |
| Feature part | describes what it is | `ReviewQueueTable`, `ImportSummary` | No `Wrapper`, `Container`, `Helper`, `Component`. |
| Kit component | Figma name without `Web/` | `StatusTag`, `DataTable`, `FormField` | Must match the Figma kit name (see [07](07-ui-and-styling.md)). |

## 3. Code identifiers

| Kind | Convention | Example |
|---|---|---|
| Component | `PascalCase` | `TicketDecisionActions` |
| Props type | `<Component>Props` | `RejectTicketModalProps` |
| Hook | `use` + `PascalCase` | `useApproveTickets` |
| Type / type alias | `PascalCase`, no `I`/`T` prefix | `ReviewQueueFilters` |
| Variable / function | `camelCase` | `selectedTicketIds`, `formatDateTime` |
| Boolean | `is`/`has`/`can`/`should` prefix | `isLoading`, `canApprove` |
| Event prop / handler | `onX` prop, `handleX` function | `onConfirm={handleConfirm}` |
| Module-level constant | `UPPER_SNAKE_CASE` | `REVIEW_QUEUE_POLL_MS = 5_000` |
| Fixed list of values | `as const` array + union type | see below |
| Route path param | `camelCase` + `Id` | `/tickets/:ticketId` |
| URL search param | `camelCase` | `?department=…&tab=csv` |
| CSS Module class | `camelCase` | `.selectionBar` → `styles.selectionBar` |
| Feature routes export | `<feature>Routes` (camelCase) | `reviewRoutes`, `ticketImportRoutes` |

**No TypeScript `enum`.** Use a union of string literals (and an `as const` array if you need to loop):

```ts
// ✅ Do
export const REVIEW_DECISIONS = ['APPROVE', 'REJECT', 'REQUEST_CHANGES'] as const;
export type ReviewDecision = (typeof REVIEW_DECISIONS)[number];

// ❌ Don't
enum ReviewDecision { Approve = 'APPROVE', Reject = 'REJECT' }
```

*Why:* `enum` is not plain JavaScript (it emits runtime code and is rejected by the
`erasableSyntaxOnly` compiler option we use), and API value types are generated by orval as unions anyway.

## 4. Query keys

Use the query-key functions that orval generates next to each hook
(`getGetReviewQueueQueryKey()`), never hand-written arrays. *Why:* the key always matches the request,
so invalidation after a mutation cannot silently miss. Details in [06](06-data-layer.md).

## 5. Business vocabulary (from the glossary — use exactly)

Code names follow the API (generated); UI text follows the SRS. The API value spellings below are what
our committed OpenAPI stub uses; if the backend publishes different spellings, the generated code wins
and this table is updated.

| Glossary term | In code | API values | UI text (exact) |
|---|---|---|---|
| Workspace | `workspace` | — | Workspace |
| Department | `department`, `departmentId` | status `ACTIVE`, `DELETED` | Department |
| Project | `project`, `projectId` | status `ACTIVE`, `REMOVED` | Project · Active / Removed |
| Jira project | `jiraProjectKey` | — | Jira project key |
| Project member | `projectMember`, `members` | — | Members |
| Role | `Role` | `ADMIN`, `DEPARTMENT_MANAGER`, `PROJECT_MANAGER`, `STAFF` | Admin · Department Manager · Project Manager · Staff |
| User account status | `userStatus` | `ACTIVE`, `DEACTIVATED` | Active / Deactivated |
| Ticket | `ticket`, `ticketId` | — | ticket / Ticket |
| Source ticket ID | `sourceTicketId` | — | Ticket ID |
| Solution | `solution` (a **field of Ticket**, never its own entity or type) | — | Solution |
| Evidence | `evidence`, `evidenceFiles` | — | Evidence (**never** "Attachment" in UI) |
| Author | `author` | — | Author |
| Ticket status | `TicketStatus` | `PENDING_REVIEW`, `CHANGES_REQUESTED`, `PUBLISHED`, `REJECTED`, `UNPUBLISHED`, `EXPIRED` | Pending review · Changes requested · Published · Rejected · Unpublished · Expired |
| Ticket source | `TicketSource` | `SOLUTION_FORM`, `JIRA_IMPORT`, `CSV`, `MANUAL` | Solution Form · Jira import · CSV · Manual |
| Review Queue | `reviewQueue` | — | Review Queue |
| Review decision | `ReviewDecision` | `APPROVE`, `REJECT`, `REQUEST_CHANGES`, `UNPUBLISH`, `REPUBLISH`, `SEND_BACK` | Approve · Reject · Request changes · Unpublish · Re-publish · Send back to queue |

| Feedback | `feedback`, `isHelpful` | — | Helpful / Not helpful |
| Search | `search`, `searchQuery` | — | Search |
| Audit log entry | `auditEntry` | — | Audit Log |
| Connection status | `connectionStatus` | `CONNECTED`, `NOT_CONNECTED` | Connected / Not connected |

Status labels shown in the UI come from one place — `StatusTag`'s label map — never typed again in a page.

### Words that must never appear (code, UI text, test data, comments)

| ❌ Never | ✅ Use |
|---|---|
| Cluster, Cluster Review, batch review | (removed — tickets are reviewed one by one) |
| Defer, Deferred, skip, snooze | (removed — an undecided ticket stays in the Review Queue) |
| Bulk sync, sync history, scheduled sync | Jira import, Import History |
| Knowledge article, KB article, candidate, solution version | Solution / Ticket |
| Attachment (in UI) | Evidence |
| PM, Reviewer, Approver | Project Manager |
| Team, group (for a Department) | Department |
| Case, issue, record (for a T-Solve Ticket) | Ticket (*issue* only means a Jira issue) |
| Unassigned Department | (removed) |
| Approved solution / Published solution | Published ticket |
| Hidden, archived (for Unpublished) | Unpublished |
| Jira statuses (Open, In Progress, Resolved) as ticket statuses | the six T-Solve statuses above |

Also never add a **Project filter** to any screen — only a sortable Project column (UI decisions 04/10).

*Why:* the team and the examiners read the SRS, Figma and the running app side by side. One word per
concept removes a whole class of "is this the same thing?" questions.

## 6. MSG codes

MSG codes are written as string literals typed `MsgCode` (`'MSG18'`), always with the `MSG` prefix and
two digits. Retired codes (MSG09, MSG11–15, MSG17, MSG23–28, MSG37, MSG48, MSG49, MSG69) do not exist
in the catalog, so TypeScript rejects them.
